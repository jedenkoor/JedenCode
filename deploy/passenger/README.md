# Этап 0. Проверка Nuxt SSR на shared-хостинге

Цель — проверить, что Nuxt Nitro запускается через Passenger на техническом
адресе хостинга, не трогая основной домен `jedenkoor.ru`.

## Что уже проверено локально

- `npx nuxt build` собирает `.output/server/index.mjs`.
- `node .output/server/index.mjs` запускается и отдаёт страницы.
- Nitro читает порт из `NITRO_PORT` или `PORT` — Passenger может передать его сам.

## 1. Собрать серверную сборку

В корне проекта:

```bash
npx nuxt build
```

Не использовать `npm run build`: текущий скрипт делает `nuxt generate`, а для
этапа 0 нужен `nuxt build`.

После сборки должны появиться:

```text
.output/server/index.mjs
.output/server/chunks/
.output/public/
```

## 2. Загрузить тест на технический адрес

По SFTP загрузить в домашнюю папку технического домена, например
`~/domains/<domain>/`:

```text
app.js                 ← из deploy/passenger/app.js
.output/server/
.output/public/
```

`app.js` должен лежать рядом с `.output`.

## 3. Настроить домен в панели хостинга

В разделе «Управление → Настройки веб-сервера» для технического домена:

- домашняя папка: `~/domains/<domain>`;
- интерпретатор: **NodeJS 22**;
- папка для статики: `.output/public`;
- сохранить и перезагрузить веб-сервер.

Если панель не принимает относительный путь для статики, указать полный путь
к `.output/public` и сообщить об этом.

## 4. Проверить

Открыть:

- `http://<domain>/`
- `http://<domain>/ru`
- `http://<domain>/ru/unknown-page`

Последний URL важен: он должен вернуть HTML Nuxt, а не стандартную страницу
Apache. Это покажет, что запросы действительно обрабатывает Nitro.

Также проверить:

```bash
curl -I http://<domain>/
```

Ожидается `200` и HTML Nuxt.

## 5. Если ошибка

Прислать:

- HTTP-статус и текст страницы;
- строки из лога ошибок хостинга;
- вывод консоли, если доступна;
- точный путь, куда загружен `app.js`;
- выбранный интерпретатор и папку статики.

Типичные причины:

- `500` — Passenger не смог загрузить `app.js` или `.output/server/index.mjs`;
- `502` — Node-процесс не слушает порт, который передал Passenger;
- `403` — неверная домашняя папка или права;
- пустая страница — статика отдаётся Apache, а Node-приложение не запустилось.

## Если Passenger пишет `Cannot find module .../.output/server/index.mjs`

Значит `app.js` уже загружен и Passenger его запустил, но папка `.output`
отсутствует или лежит не там.

Проверить по SSH/консоли:

```bash
cd ~/domains/<domain>
ls -la
ls -la .output/server
```

`app.js` и `.output` должны быть на одном уровне. Частая причина — SFTP-клиент
не показывает и не загружает папки, начинающиеся с точки. В FileZilla включить
«Сервер → Показывать скрытые файлы» или загрузить архивом.

Готовый архив для загрузки: `ssr-spike.zip` (`app.js` и `.output` внутри).
Загрузить архив в домашнюю папку домена, распаковать и перезагрузить
веб-сервер.

## Результат этапа 0

Проверено на `<domain>`:

- `https://<domain>/` — `200`, HTML Nuxt;
- `https://<domain>/ru` — `200`, русская версия;
- `https://<domain>/ru/unknown-page` — `200`, HTML Nuxt, а не страница Apache.

Passenger запускает `app.js`, Node 22, приложение работает.

Замечание по деплою: FTPS хостинга обрывает длинную сессию на большом
`server/node_modules`. Загружать его нужно пакетами или через SFTP.
Для следующих этапов стоит сделать нормальный деплой по SSH/SFTP.

## Ограничения этапа 0

- Основной `jedenkoor.ru` не меняем.
- `nitro.prerender.routes` пока остаются в конфиге, поэтому `/` и `/projects`
  могут отдаваться как заранее собранные страницы. Для проверки SSR используем
  `/ru/unknown-page`.
- Python-бэкенд, Django, MySQL и API на этом этапе не трогаем.
